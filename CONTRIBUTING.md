# Как работаем командой

Цель: **никто никого не блокирует, `main` всегда запускается и показывается жюри.**

## 1. Команда и зоны ответственности

Заполните при старте. Зона = папки, в которых вы главный; в чужую зону — только через договорённость в чате.

| Роль | Кто | Зона |
|---|---|---|
| AI / ML | Владимир | `apps/api/app/ai/`, `apps/api/app/data/knowledge/` |
| Backend / интеграции | Нуржан | `apps/api/app/api/`, `apps/api/app/schemas/`, `apps/api/app/core/` |
| Frontend | Дамир | `apps/web/` |
| Продукт / питч / QA | Фархат | `docs/`, `demo_cache.json`, слайды, видео |

Общие файлы (правим аккуратно, предупреждаем в чате): `.env.example`, `Makefile`, `package.json`, `requirements.txt`, `docs/`.

## 2. Git-процесс (trunk-based, без ритуалов)

- `main` — всегда рабочий. **Прямых пушей в `main` нет**, только PR (включите Branch protection: require PR, запретить force-push; required reviews не включаем — они тормозят).
- Ветки короткоживущие (до ~3 часов): `feat/<NNN>-<кто>-<что>` (NNN — номер спеки), `fix/<что>`, `spec/<NNN>-<slug>`. Пример: `feat/002-aida-rag-search`.
- **Мёржим в `main` каждые 2–3 часа**, даже недоделанное, если не ломает запуск (прячем за флагом или не подключаем в UI). Долгие ветки = конфликты за час до дедлайна.
- **Синхронизация — правило, а не пожелание.** `make sync` (fetch + rebase на `origin/main`, ваши незакоммиченные правки сохраняются) запускаем:
  1. в начале смены и после сна;
  2. перед созданием новой ветки;
  3. перед открытием PR и перед мёржем;
  4. когда в чате написали «замёржил».

  `make sync` покажет, что пришло, и подскажет, что делать: изменились зависимости → `make install`, `.env.example` → сверить `.env`, правила/доки → прочитать, контракт чата → проверить свой код. То же самое подсказывает хук `post-merge` после обычного `git pull`, а `pre-push` предупреждает, если `main` ушёл вперёд.
- Перед PR: `make sync`, `make fmt`, `make check`.
- Ревью: **быстрое, ≤15 минут**, один человек из другой зоны. Смотрим «запускается ли и не ломает ли контракт», а не стиль (стиль делает форматтер). Если в 3 ночи некому — мёржит автор, но пишет в чат.
- Merge — **squash**, заголовок в формате `feat: ...`, `fix: ...`, `docs: ...`, `chore: ...` (для фич по спеке — `feat(NNN): ...`).
- Конфликт? Тот, кто мёржит вторым, разруливает у себя локально.

## 3. Работаем по спеке

Правила и процесс — в [`specs/README.md`](specs/README.md) (читается за 3 минуты). Суть:

- **Спека — источник правды.** Фича >1 часа, или с контрактом, или на 2+ зоны сначала получает спеку `specs/NNN-slug.md` (одна страница, по `_template.md`), потом код. Мелочи и багфиксы — без спеки.
- **Спека согласована = смёржена в `main`** (быстрое ревью, смотрят владельцы затронутых зон). До этого код по ней не пишем.
- **Делаем только то, что в спеке.** Хочется больше — правим спеку (в том же PR) или пишем в «потом». Расхождение кода и спеки — это баг одного из них.
- **Распределение работы — таблица «Задачи по зонам»** в спеке. Не ваша строка — не ваша задача.
- В PR с кодом: заголовок `feat(NNN): …`, ссылка на спеку, отмеченные AC. Фича `done`, когда AC проверены, работает `DEMO_MODE` и демо-сценарий прошёл человек, не писавший код.
- `make specs` (входит в `make check` и CI) проверяет форму спек. `/spec <идея>` и `/spec-check NNN` — команды для Claude Code.
- Продукт целиком — `specs/000-product.md`: заполняем вместе в часы 0–1, оттуда берём питч.

## 4. Контракт между фронтом и бэком

Единственное место, где зоны пересекаются — поток событий чата:

- Бэкенд: `apps/api/app/ai/router.py` (docstring) и `schemas/`
- Фронт: `apps/web/src/features/chat/types.ts`

Правила:
1. Меняем **оба конца и раздел «Контракт» в спеке в одном PR** (или сначала добавляем поле необратимо-совместимо, потом удаляем старое).
2. Новые поля — опциональные. Не переименовываем, а добавляем рядом.
3. Любое изменение контракта — сообщение в чат: «поменял X в событии Y».

## 5. Демо-безопасность

- `main` обязан работать с `DEMO_MODE=true` **без интернета и ключей**. Новая фича без ответа в `demo_cache.json` / без мок-ветки — не готова.
- Ключи только в `.env` (он в `.gitignore`). Утекло в коммит — немедленно отозвать ключ, а не «переписывать историю».
- Каждые 6 часов: свежий `git clone` → `make install` → `DEMO_MODE=true make -j2 dev` у кого-то, кто не писал код. Так ловим «у меня работает».

## 6. Коммуникация

- Один чат, один канал «сломался main» — туда пишут сразу, чинят первым делом.
- Синк по 5 минут: старт смены, 12:00, 18:00 (кто что делает, кто чем блокирован).
- Не знаешь, где чья зона, — спрашивай, не угадывай. Чужие файлы без предупреждения не переписываем и не реформатируем.
- Идея вне MVP → в список «потом» в `docs/ROADMAP.md`, не в код. После feature freeze (час 36) — **только багфиксы**.

## 7. Стиль кода

Не обсуждаем — это решает форматтер. Структура папок — см. [ARCHITECTURE.md](docs/ARCHITECTURE.md).

### Pre-commit хук

Включается автоматически в `make install` (или вручную `make hooks`), лежит в `.githooks/` (там же `post-merge` и `pre-push` из раздела про синхронизацию). `pre-commit` на каждый коммит за секунды:

1. блокирует `.env` и строки, похожие на API-ключи (`sk-ant-…`, `sk-…`, `AKIA…`);
2. **сам форматирует** застейдженные `.py` (ruff) и `.ts/.tsx/.css/.json/.md` (prettier) и добавляет исправления в коммит;
3. гоняет `tsc`, если трогали TypeScript.

Полная проверка со сборкой — `make check` (её же делает CI). Срочно, а хук мешает: `git commit --no-verify` — CI всё равно проверит. Если застейджили часть файла через `git add -p`, хук отформатирует и добавит файл целиком.

Если работаете с Claude Code или другим ИИ-агентом — он читает [CLAUDE.md](CLAUDE.md).
